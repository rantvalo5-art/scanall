  1. ¿Cada cuánto re-correr el backtest?

  El backtest es determinístico sobre datos históricos. Casos donde corresponde
  re-correr:

  - Siempre: cambiaste config o código de scoring (validación obligatoria).
  - Semanal: sobre la última ventana de 7 días (lo que ya hacés) — detecta si tu
   config sigue funcionando con el último régimen.
  - Mensual: sobre 3-4 ventanas temporales distintas (ej: las últimas 4 semanas
  separadas) — detecta overfitting. Si una config ganadora sólo brilla en 1
  ventana, está sobreajustada.
  - Cuando el régimen cambia: bull → bear, alta vol → consolidación. La config
  óptima en bull no suele serlo en bear.

  Tu corrida actual con --weeks 1 es buena para iterar rápido pero no valida 
  robustez — el sweet spot real se encuentra promediando varias ventanas.

  2. ¿Qué settings conviene volver a probar?

  Alto impacto (los que más mueven la aguja):
  - scoring.STRONG_MIN_SCORE (10-13) — controla el tamaño del bucket STRONG
  - scoring.BEST_MIN_SCORE (12-14) — controla BEST
  - indicators.ATR_MIN_PCT (0.8-2.0) — filtro principal de calidad (J probó 1.5)
  - STRUCT_PENALTY en prebreak/breakout/hold (-1 a +1) — M lo flippeó
  - scoring_breakout.OBV_TIER_*_BONUS — bonos OBV son los que más suman

  Medio impacto:
  - breakout.BREAKOUT_MIN_VOL_RATIO (1.5-3.0)
  - prebreak.PREBREAK_NEAR_MAX (0.005-0.015)
  - scoring_*.CVD_TIER_* bonuses

  Bajo impacto (ya viste, no mueven):
  - HOLD pullback/recent_break (K fue no-op)

  3. ¿Cómo encontrar el sweet spot?

  Tres pasos:

  a) Definir una métrica objetivo única (no podés optimizar 4 cosas a la vez).
  Ejemplo:
  score = catch_rate_BEST_STRONG * 0.5
        + win_pct_>10%_en_BEST * 0.3
        + min(1, BEST_per_day / 15) * 0.2     ← penaliza si <15/día
        - max(0, BEST_per_day - 25) / 25 * 0.2 ← penaliza si >25/día
  Esto convierte cada backtest en un número único comparable.

  b) Sweep sistemático en vez de variantes manuales. En lugar de inventar

> ok ahora explicarme como los uso sweep y harnessing?                          

● "Harness" es el mismo sweep.py — es el término para un script que orquesta
  otras herramientas automáticamente. No son dos cosas distintas.

  ---
  Workflow completo paso a paso

  1. Configurar la grilla (sweep_example.json)

  Editás qué parámetros querés explorar y con qué valores:

  "params": {
    "indicators.ATR_MIN_PCT":          [1.0, 1.5, 2.0],
    "scoring.STRONG_MIN_SCORE":        [11, 12],
    "scoring_breakout.STRUCT_PENALTY": [-1, 0, 1],
    "scoring_hold.STRUCT_PENALTY":     [-1, 0, 1]
  }

  Esto genera 3×2×3×3 = 54 combinaciones. Cualquier key de config.json se agrega
   con formato "seccion.KEY": [valores].

  Las windows son las fechas de fin de cada semana a evaluar:
  "windows": ["2026-05-09", "2026-05-02", "2026-04-25"]
  Cada ventana prueba la misma grilla en una semana distinta del pasado →
  detecta si el ganador es robusto o fue suerte.

  ---
  2. Primer run (smoke test)

  Antes de correr las 54×3 corridas, verificá que no crashea con algo liviano.
  Creá un sweep_test.json mínimo:

  {
    "base": "config.json",
    "weeks": 1,
    "max_pairs": 30,
    "scan_interval_min": 30,
    "windows": ["2026-05-09"],
    "params": { "scoring.STRONG_MIN_SCORE": [11, 12] },
    "out_dir": ".sweep_test"
  }

  python sweep.py sweep_test.json

  Debería completar en 2-3 minutos y mostrar un ranking de 2 configs.

  ---
  3. Sweep completo

  python sweep.py sweep_example.json

  Qué pasa internamente:
  1. Genera 54 archivos cfg_0000.json … cfg_0053.json en .sweep_results/
  2. Lanza las 3 ventanas en paralelo (3 subprocesos simultáneos)
  3. Cada subproceso corre backtest.py --variants config.json cfg_0000.json … 
  cfg_0053.json --end-date YYYY-MM-DD — UNA descarga de klines, 54 variantes
  encima
  4. Output de cada ventana va a .sweep_results/window_YYYY-MM-DD.log (no se
  mezcla en pantalla)
  5. Al terminar las 3 ventanas: parsea resultados, promedia scores, imprime
  tabla

  Verás en pantalla algo así:

    [2026-05-02] OK
    [2026-04-25] OK

  ---
  4. Leer los resultados

  Las columnas clave:

  Col: score
  Qué significa: Métrica compuesta (0-1)
  Target: Mayor es mejor
  ────────────────────────────────────────
  Col: std
  Qué significa: Variación del score entre las 3 semanas
  Target: < 0.05 = robusto; > 0.10 = posible overfitting
  ────────────────────────────────────────
  Col: catch
  Qué significa: Cuántos de los top-30 movers cayeron en BEST+STRONG
  Target: Mayor es mejor
  ────────────────────────────────────────
  Col: win10%
  Qué significa: % de alertas BEST que subieron >10% en 24h
  Target: Mayor es mejor
  ────────────────────────────────────────
  Col: best/d
  Qué significa: Alertas BEST por día
  Target: Target: 10-20
  ────────────────────────────────────────
  Col: rr
  Qué significa: Reward/Risk en bucket BEST
  Target: Mayor es mejor

  Regla de decisión: el #1 por score no siempre es el mejor. Preferí configs con
   std < 0.05 (consistentes entre semanas) sobre configs con score más alto pero
   std > 0.10.

  ---
  5. Promover el ganador

  :: Copiar el config ganador para inspeccionarlo
  copy .sweep_results\cfg_0027.json config_winner.json

  :: Validar contra 4 semanas completas
  python backtest.py --weeks 4 --compare config.json config_winner.json --out

  :: Si los números se mantienen, es candidato a producción

  ---
  6. Iterar

  Después del primer sweep, afinás la grilla alrededor del ganador. Si el #1
  tuvo ATR=1.5, en el siguiente sweep probás [1.3, 1.5, 1.7] — buscás el óptimo
  local. Cada iteración tarda lo mismo pero explora un rango más fino.
